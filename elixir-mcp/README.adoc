= feedback-o-tron engine
:toc: macro
:toclevels: 2

The Elixir/OTP engine behind feedback-o-tron. If you are installing the tool
rather than working on it, read the repository root's `README.adoc` instead.

toc::[]

== Build

[source,bash]
----
mix deps.get
mix escript.build          # produces ./feedback-o-tron
./feedback-o-tron --version
----

Requires Elixir 1.16 or newer on OTP 26 or newer. CI tests 1.15, 1.16 and
1.17 on OTP 26, plus 1.19 on OTP 27, which is what this engine is developed
against.

== Run

[source,bash]
----
./feedback-o-tron serve
----

`serve` runs everything in one OS process and opens two doors:

[cols="1,3"]
|===
|Door |What it is

|MCP (stdin/stdout)
|JSON-RPC 2.0 for MCP hosts. The process exits when stdin closes, so a host
that goes away leaves no orphan.

|HTTP intake
|`127.0.0.1:7722`. `GET /health` answers
`{"status":"ok","service":"feedback-o-tron","intake":"http"}`.
|===

Close either with `--no-stdio` or `--no-http`; closing both is an error.
`--http-port N` moves the intake.

`FeedbackATron.Doors.config/2` is the single place that decides which doors
open. It reads application environment first, then OS environment:
`FEEDBACK_O_TRON_MCP`, `FEEDBACK_O_TRON_HTTP`, `FEEDBACK_O_TRON_HTTP_PORT`,
`FEEDBACK_O_TRON_HTTP_BIND`.

== The TCP transport

An optional third door, off by default, for hosts that speak line-delimited
JSON-RPC over a socket rather than over stdio:

[source,bash]
----
FEEDBACK_A_TRON_MCP_TCP=1 ./feedback-o-tron serve
----

It binds `127.0.0.1:7979`. `FEEDBACK_A_TRON_MCP_TCP_PORT` and
`FEEDBACK_A_TRON_MCP_TCP_BIND` change that.

NOTE: These three names keep the older `A_TRON` spelling because that is what
`mcp/server.ex` reads. Renaming the `FeedbackATron` namespace is a separate,
mechanical follow-up; until it lands, this document prints the names the code
actually looks for.

Smoke-test it with `scripts/mcp_tcp_smoke_test.sh`, which needs `nc`
installed and the server already running.

== Tools the MCP door offers

Three, registered in `doors.ex` and handed to the MCP server as its tool
list:

[cols="1,3"]
|===
|Tool |What it does

|`submit_feedback`
|Draft and (outside SP1b) submit a report to one or more platforms.

|`research_feedback`
|Look for existing reports before filing a new one.

|`synthesize_feedback`
|Turn a rough description into a structured report.
|===

`migration_observe` is implemented under `mcp/tools/` but is *not* registered,
so it does not appear in `tools/list`. Treat it as unwired.

== Nothing sends without a person

`submit` prints the entire payload and waits for a typed `y`. With no
terminal on stdin it refuses and exits 3. There is no `--yes` flag. Use
`--dry-run` to print the payload and send nothing.

The MCP and HTTP doors accept and draft reports; they do not send.

== Test

[source,bash]
----
mix test                   # unit tests
mix escript.build && mix test --only escript   # end-to-end, against the binary
mix format --check-formatted
mix compile --warnings-as-errors
----

The `:escript` tag is excluded by default (`test/test_helper.exs`) because
those tests exec a binary that may not be built.

== Layout

....
lib/feedback_a_tron/
├── cli.ex                 # argv parsing, run/2, exit codes
├── doors.ex               # which doors open
├── submitter.ex           # platform dispatch, dedupe, rate limiting
├── credentials.ex         # env, then the gh CLI
├── audit_log.ex           # JSON-lines audit trail
├── mcp/
│   ├── server.ex          # JSON-RPC over stdio and optional TCP
│   └── tools/             # the three registered tools, plus migration_observe
└── http_intake/
    └── router.ex          # Plug router: /health, /api/v1/*
....
